# RAG 检索测试报告（RAG_TEST_REPORT）

> 实测：本系统 RAG 不是"按查询返回 top-k chunk"，而是——正文生成前，内容计划为每个章节分配 `knowledge.item_ids`（来源 = 绑定知识库文档的所有条目），并在每章 prompt 注入对应条目 + 全局事实。

## 检索机制观察（实测）
- 绑定知识库文档：`doc-20df2651…`（《圣起过轨吊投标文件.pdf》，26 个条目，status=success）。
- 每章内容计划 `plan_json` 含：
  - `writing_focus`：本章写作大纲/重点。
  - `knowledge.item_ids`：本章选定使用的知识条目。
  - `facts.titles`：本章应使用的全局事实。
- 正文生成读取绑定文档的 `knowledge_items`（title/resume/content）注入 prompt（`renderKnowledgeItemsForPrompt`）。

## 观察
- 3/4 个技术章节正确命中相关知识条目（安装→施工方案、售后/培训→技术服务售后），说明"绑定文档 + 内容计划 item_ids"的 RAG 是**有效**的，能提升内容专业度（正文出现 无损检测/探伤合格后/出厂前空载轻载全载超载试验 等来自知识与招标结合的表述）。
- 1 个章节（设备供应与现场就位）分配到空 item_ids，漏配了知识库中"产品包装与运输方案(K000011)、交货进度安排(K000009)"等高度相关条目 → 检索/AI 映射存在缺口。

## RAG Scope 验证（§18）
- 系统未实现 company/project/category 等显式 scope 字段参与检索；检索粒度 = "整份文档条目全集 + 内容计划 item_ids 过滤"。因此"scope A vs scope B"对比不适用。可确认：item_ids 过滤确实生效（不同章节分配不同 item_ids，而非每章都用全集）。

## RAG 为空时的行为（§19）
- 未做"移除某技术信息"的专门对照实验；但 6.1.1（item_ids 为空、无对应知识）生成的正文并未编造企业已有产品的具体参数/案例，而是基于招标参数（MG200T 等）+ 通用工程方法展开，符合"方案性描述而非虚构企业参数"的预期。→ 未见 P1 编造问题。

## 判定
- Retrieval Quality：**PARTIAL**
  - 优点：按章节分配知识条目有效，命中率高（3/4），内容专业度提升明显。
  - 不足：非按查询检索、无 scope 维度、部分章节漏配同库高相关条目；模板填充/点对点类（技术偏离表等）未走 RAG 生成正文（为空）。
